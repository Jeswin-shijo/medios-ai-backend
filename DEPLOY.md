# Deploying MediOS

The web app runs on Vercel, the API on Render, and the database on MongoDB Atlas. Do the steps in this order. Each one needs a value from the step before it.

```
Browser ──> Vercel (web app, static files)
   └──────> Render (this API, always on) ──> MongoDB Atlas
SnapServe ─> Render (call webhooks)
```

The API cannot run on Vercel. It keeps live connections open for the Token Queue screen and the waiting-room display, and it runs a call scheduler every minute. Vercel functions do neither, and free plans that sleep break both, so Render uses the paid Starter plan.

## 1. Database: MongoDB Atlas

1. Create a cluster in **AWS Singapore (ap-southeast-1)**, the same region as the Render service.
   - M0 (free) is fine for a demo.
   - Use M10 or larger for real patients: it adds backups and more storage.
2. Under **Database Access**, add a database user with a long random password and the *Read and write to any database* role.
3. Under **Network Access**, allow Render's outbound IP addresses. To find them, open the Render service and go to **Connect**, then **Outbound**. Until the service exists you can allow `0.0.0.0/0`, but replace that afterwards.
4. Under **Connect**, then **Drivers**, copy the connection string and add the database name before the `?`:
   `mongodb+srv://USER:PASSWORD@CLUSTER.mongodb.net/medios_hospital?retryWrites=true&w=majority`

**Patient data and India.** If the hospital requires patient data to stay in India, Render is the wrong host, because its closest region is Singapore. In that case:
- Run the API on DigitalOcean App Platform (Bangalore) or AWS (Mumbai).
- Put the Atlas cluster in Mumbai (ap-south-1).
- The settings below stay the same.

## 2. API: Render

**New service.** Choose **New**, then **Blueprint**, then this repository. Render reads [`render.yaml`](render.yaml) and asks for the values marked `sync: false`:

| Setting | Value |
|---|---|
| `MONGODB_URI` | The Atlas connection string from step 1 |
| `CORS_ORIGIN` | The Vercel address from step 4, e.g. `https://medios.vercel.app`. Enter a placeholder for now and update it after step 4. |
| `SNAPSERVE_*`, `CALL_WEBHOOK_SECRET`, `CALL_TOOLS_SECRET`, `CALL_ALLOWED_NUMBERS` | Leave these empty for now. The call agent stays off (`CALL_PROVIDER=none`) until step 6. |

**Existing web service.** If you created the service by hand, copy the build command, start command, health check path, region, plan and every setting from [`render.yaml`](render.yaml) into its **Settings** and **Environment** pages.

`JWT_SECRET` is generated by Render. Don't set `CLINIC_DATE`: it pins the clinic's date to the demo day.

When the deploy finishes, `https://<service>.onrender.com/api/health` should return `{"success":true, … "status":"ok"}`. Every push to `main` deploys again.

## 3. First accounts

A new database is empty. Create the first admin from your machine, pointing at Atlas:

```bash
MONGODB_URI='mongodb+srv://…/medios_hospital?…' \
USER_EMAIL='admin@yourhospital.in' USER_PASSWORD='…' USER_NAME='Hospital Admin' \
npm run create-user
```

- Run it again for each doctor or staff member, with `USER_ROLE` set to `doctor`, `nurse`, `pharmacist`, `lab` or `staff`. Doctors can also have `USER_SPECIALTY`.
- Passwords need at least 8 characters, with upper and lower case letters, a number and a symbol.
- Running it again for an existing email resets that account's password and signs out its sessions.

`npm run seed` loads the demo hospital instead. It wipes the database first and creates demo logins whose password is published (`Admin@123`). It refuses any database that isn't on this machine unless you set `SEED_ALLOW_REMOTE=true`. Only do that for a throwaway demo database.

**Demo password on a remote database.** The seed gives every demo login the password in `SEED_DEMO_PASSWORD`. Without it, `Admin@123` is used only when `MONGODB_URI` points at `localhost` or `127.0.0.1`; a seed against any other host refuses to run, before it wipes anything. Seeding the Atlas demo therefore needs `SEED_DEMO_PASSWORD='<private password>'` (the scheduling seed adds 12 more doctor logins and uses the same password, so all 19 demo logins get it).

Then replace the demo passwords straight away if you seeded without `SEED_DEMO_PASSWORD`. Run `npm run create-user` (same `MONGODB_URI`) once per demo login, with a new `USER_PASSWORD` and the login's own `USER_ROLE` (create-user also sets the role, and defaults to `admin`):

| `USER_EMAIL` | `USER_ROLE` |
|---|---|
| `admin@medios.ai` | `admin` |
| `doctor@medios.ai` | `doctor` |
| `nurse@medios.ai` | `nurse` |
| `frontdesk@medios.ai` | `staff` |
| `pharmacy@medios.ai` | `pharmacist` |
| `lab@medios.ai` | `lab` |
| `pathologist@medios.ai` | `lab` |
| `arun@`, `priya@`, `meena@`, `rajesh@`, `john@`, `lakshmi@`, `suresh@`, `kavitha@`, `vinod@`, `anand@`, `anitha.anaesthesia@`, `ravi.radiology@medios.ai` | `doctor` (added by the scheduling seed) |

## 4. Web app: Vercel

1. Import the web app repository (`medi-os-ai`). Vercel reads its `vercel.json`, so no build settings need changing.
2. Add `VITE_API_URL=https://<service>.onrender.com/api` under **Settings**, then **Environment Variables**. The build fails with a message if it is missing.
3. Deploy. Copy the Vercel address into Render's `CORS_ORIGIN` (step 2); Render redeploys by itself.
4. Sign in with the account from step 3.

The waiting-room display and the check-in kiosk open at `/display#key=…` and `/kiosk#key=…` on the Vercel address. Add them from the Token Queue screen, under **Displays & Settings**.

## 5. Staying signed in on iPads and Safari

On `*.vercel.app` and `*.onrender.com`, the browser treats the web app and the API as different sites. So the sign-in cookie is a cross-site cookie (`COOKIE_SAMESITE=none`):

- **Chrome, Edge and Firefox** keep it.
- **Safari**, on every iPhone and iPad, blocks it. Sign-in still works, but reloading the page, or 15 minutes after signing in, signs the user out.

To fix it, put both under one domain you own:

1. In Vercel, add the custom domain `app.yourhospital.in`. In Render, add `api.yourhospital.in`. Each shows the DNS record to create.
2. Set `VITE_API_URL=https://api.yourhospital.in/api` in Vercel, and redeploy.
3. In Render, set `CORS_ORIGIN=https://app.yourhospital.in` and `COOKIE_SAMESITE=lax`.

## 6. AI call agent (when ready)

1. In Render, set the following:
   - `SNAPSERVE_API_KEY`, `SNAPSERVE_CONFIRMATION_AGENT_ID` and `SNAPSERVE_BOOKING_AGENT_ID`;
   - `CALL_WEBHOOK_SECRET`, which must be letters and digits only (generate one with `openssl rand -hex 24`);
   - `CALL_PROVIDER=snapserve`.
2. In both SnapServe agents, set the post-call notify URL to `https://<api-address>/api/calls/webhook/snapserve`, and send `CALL_WEBHOOK_SECRET` in an `X-MediOS-Webhook-Token` header. If SnapServe only takes a URL, use `https://<api-address>/api/calls/webhook/snapserve?token=<CALL_WEBHOOK_SECRET>` instead.
3. Optional settings:
   - **Calls to the hospital (inbound):** `SNAPSERVE_INBOUND_AGENT_ID` and `CALL_TOOLS_SECRET` (24+ characters, `openssl rand -hex 24`). The tools are on only while `CALL_PROVIDER=snapserve`.
   - **Signed webhooks:** `SNAPSERVE_SIGNING_SECRET`, SnapServe's signing secret.
   - **Testing real calls:** `CALL_ALLOWED_NUMBERS`, comma-separated. No other number is dialled. Remove it for go-live.

The API refuses to start if `CALL_PROVIDER=snapserve` is set without the values in step 1. The error message names the missing one.

## 7. AI bed suggestions

The Beds screen suggests where to admit a patient. The rules always work; AI only reorders and explains the top beds. `AI_PROVIDER` picks the mode (`none` is the default in production):

- **Demo on Render:** `AI_PROVIDER=sample`. Answers are canned and marked SAMPLE, and no key is needed. `render.yaml` sets this.
- **Real AI:** set `AI_PROVIDER=claude` and add `ANTHROPIC_API_KEY` in the host's dashboard (Render: Environment). Optional: `AI_MODEL` (default `claude-opus-5-5`) and `AI_TIMEOUT_MS` (default 8000). Never put the key in chat, in the repo or in `render.yaml`.
- Changing settings in Render is the owner's call: confirm before you change them. Editing `render.yaml` only takes effect after it is pushed and Render syncs the Blueprint.
- Then open Settings, AI Assistant and press **Check connection**. An admin can also switch AI bed suggestions off there without touching the host.
- Load the hospital's real wards and beds with `npm run import-beds` (see the README) instead of the demo seed.

## 8. Reception kiosk (before real patients)

1. **Payments and SMS.** Real UPI, card-machine and SMS providers are **not built yet**: only `sample` and `none` exist.
   - `render.yaml` sets `PAYMENT_PROVIDER=sample` and `SMS_PROVIDER=sample` **for the client demo only**. In sample mode payments are simulated and OTP codes appear on the kiosk, so it must **never** be used with real patients (the API logs a loud warning in production).
   - **The safe production setting is `none`** for both, which is also what a production API uses when they are unset (development defaults to `sample`): the kiosk takes cash only, confirmed by staff at the counter, and "Find my record" by mobile number is off (patients use their card, or the front desk).
   - Switch to a real provider only once one is built and connected (for example Razorpay or Pine Labs, and an SMS service).
2. **HTTPS.** The API must be served over HTTPS: kiosk keys travel in request headers.
3. **`PUBLIC_WEB_URL`** must be the web app's address (set to `https://medi-os-ai.vercel.app` for the demo); the tracking links use it.
4. **Tablet setup.** In the web app, open Token Queue > Displays & Settings, create a kiosk device and scan its setup QR from the tablet app. Removing the device revokes its key.
5. **New collections.** The reception module adds `opvisits`, `opsequences`, `receptionsessions` and `otpchallenges`, and shares `departments` and `opdoctors` with the Scheduling Agent. They are created on first use; no migration is needed.

## 9. Patient Support (family updates and check-up calls)

1. **`MESSAGE_PROVIDER=sample`** for the client demo (`render.yaml` sets it; the Render service was made by hand, so set it in the dashboard too). Updates are logged and shown as Sample; nothing is sent to anyone. In production the default is `none`: every update shows "Skipped: messaging off". A real WhatsApp or SMS provider is not built yet, and it needs Meta template approval and DLT registration first. Never claim updates are being delivered while the mode is `sample` or `none`.
2. **`TZ=Asia/Kolkata`.** Quiet hours (21:00 to 07:00), working hours and the check-up calling window follow the server's clock. Confirm `TZ` in the Render dashboard, or an update meant for the morning goes out at 02:30 to 12:30 IST.
3. **`SNAPSERVE_CHECKUP_AGENT_ID`** only once a check-up agent exists in SnapServe (a later step). Until then check-ups are made by hand.
4. **Update the SnapServe inbound agent.** In AI Call Agent → Agent Scripts, copy the new script and the tools into the agent: `hospital_info`, `expected_arrival` and the `topic` on `request_callback`. Without it, callers still work as before, but their call-backs open tickets with no topic (type Other).
5. **Seed.** The demo seed also loads the Patient Support day; reseed right before a demo (clocks run on real time). The reconcile and update passes run each minute on the API.
6. **New collections.** The Patient Support tickets, updates, check-up calls, ratings, templates and FAQs (see `src/modules/patient-support/schemas`), created on first use; no migration. Default templates and FAQs are written at start-up.
